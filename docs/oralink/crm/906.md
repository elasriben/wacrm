# CRM 906 — correction de l’ordre des consentements

Cette Pull Request est destinée à la revue de code uniquement. Elle n’autorise aucune application de migration ni aucun déploiement.

## Périmètre

La migration additive `906_oralink_consent_order_hardening.sql` corrige le passage
à 904 et les privilèges de séquence. Les migrations publiées 903/904 ne sont pas
réécrites. La migration 905, réservée à l’export CSV indépendant, n’est pas incluse.

## Trois anomalies corrigées

1. **Historique :** 900 retenait la dernière décision par date puis `seq`, tandis
   que 904 retenait le plus grand `seq`. Une ancienne valeur imposée élevée pouvait
   réactiver un accord après une révocation, puis masquer un nouveau STOP.
2. **Privilèges :** les droits par défaut pouvaient autoriser `setval`, permettant
   de déplacer le générateur partagé malgré l’attribution de `seq` par le trigger.
3. **Tests :** une erreur SQL pouvait supprimer plusieurs assertions et laisser un
   résumé vert. Le lanceur vérifie désormais erreurs, codes de sortie, résumé
   unique, nombre des assertions et correspondance avec les lignes PASS/FAIL.

## Transition et contrat d’ordre

906 ajoute un `decision_order` contrôlé par le serveur. Les événements, anciennes
séquences, dates et preuves restent inchangés. Lors de l’initialisation, une
révocation visible selon **900 ou 904** est conservée : une ambiguïté historique
n’est jamais interprétée comme un accord. Un nouveau START explicite peut ensuite
rétablir l’accord. Le rejeu de 906 ne reclasse pas l’historique.

Les nouvelles décisions suivent l’allocation d’une séquence privée `CACHE 1`.
Cet ordre n’est ni celui des COMMIT ni celui des horodatages fournisseur.
Un ancien START reçu pour la première fois après un STOP reste indistinguable
d’un nouveau START ; cette limite demande une décision métier séparée.

Le générateur, ses bornes, son propriétaire et sa dépendance sont vérifiés.
Les valeurs proposées par l’appelant sont remplacées par la garde. Les rôles
applicatifs perdent les droits permettant `setval` ; un droit dangereux hérité
fait échouer la migration. Le propriétaire et les administrateurs PostgreSQL
restent privilégiés. Aucun changement de politique RLS n’est introduit.

Ces contrôles SQL ne certifient pas les ACL d’une instance Supabase distante,
les chemins `SET ROLE` ou les schémas exposés par PostgREST.

## Vérifications reproductibles

```sh
python3 oralink/crm/tests/run-consent-order-906.py
```

Le runner utilise PostgreSQL jetable, hors réseau, avec des données fictives.
Il reproduit le défaut avant correction et contrôle la transition historique,
STOP puis START, le rejeu, les droits des rôles, deux comptes distincts, les refus
de manipulation des séquences, la concurrence et le rollback après erreur.
Il provoque aussi une vraie erreur SQL dans une copie temporaire du lanceur.
Un test manquant ou une erreur critique ne doit pas produire un succès.

Le bootstrap auth/storage est minimal : ce n’est pas une pile Supabase Auth/JWT/
PostgREST complète. Les tests applicatifs ciblés utilisent des simulations sans
appel fournisseur. Les CI prévues pour cette PR sont :

- `CRM 906 / safety` : diff, fichiers protégés/sensibles et syntaxe.
- `CRM 906 / postgres` : contre-recette sur base jetable.
- `CRM 906 / app` : tests applicatifs ciblés, TypeScript et ESLint.

## Conditions d’application — aucune exécution autorisée par cette PR

906 est un bloc `DO` atomique, avec verrou exclusif pendant l’initialisation et
la publication de la vue. L’ancien générateur est avancé avec `RESTART`
transactionnel. Une transaction extérieure peut couvrir **904 puis 906**, en
prenant le verrou sur les consentements **avant les contrôles de 904**.

Avant toute application réelle, approuver une procédure qui :

1. Inventorie versions enregistrées, objets réels, propriétaires, ACL effectives,
   capacités des séquences, sauvegarde et restauration.
2. Suspend et draine les traitements et transactions applicatives concernés : un
   verrou ne rappelle pas un consentement déjà lu ni un envoi déjà préparé.
3. Applique la paire sans exposer l’état intermédiaire de 904, vérifie les
   postconditions, coordonne l’historique Supabase et recharge le cache PostgREST.
4. Vérifie les droits et insertions légitimes avant reprise progressive.

Le CLI Supabase gère les fichiers compatibles séparément en transaction ; ne pas
supposer qu’un `db push` rend toute la paire atomique. Un lanceur SQL extérieur
ne gère pas automatiquement l’historique Supabase. Après échec, rester en maintenance
et vérifier schéma et historique avant reprise. Après succès, ne pas revenir à
904 : une correction additive ou une restauration contrôlée exige une décision.

Si 906 est enregistrée avant la future 905, prévoir séparément son arrivée hors
ordre : dry-run et insertion contrôlée, ou renumérotation explicitement autorisée.
Ne pas marquer 905 appliquée sans l’exécuter.

## Conditions de revue et limites

La fusion reste soumise à une CI verte, une revue indépendante et l’approbation
OraLink. Le déploiement reste **NO-GO** tant que les ACL réelles, l’application
contrôlée et les limites métier ne sont pas validées.

La persistance du message et celle du consentement ne deviennent pas atomiques :
une panne entre les deux reste une limite applicative héritée. 906 ne garantit
pas un traitement « exactement une fois » et ne rappelle aucun message déjà envoyé.
